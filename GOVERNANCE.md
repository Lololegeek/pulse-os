# PulseOS Governance

PulseOS uses a lightweight maintainer model while the project is young.

## Roles

### Contributors

Anyone who submits useful code, documentation, testing, design, benchmarks or bug reports is a contributor.

### Maintainers

Maintainers review and merge changes, manage releases, security response, project policy and CI infrastructure. The repository owner currently acts as the initial lead maintainer.

## Decision making

The normal process is:

1. discuss significant changes in an issue or pull request;
2. collect technical evidence and affected-user feedback;
3. seek rough consensus among active contributors;
4. a maintainer makes the final merge/release decision when consensus is unclear.

Performance decisions prioritize reproducible data over popularity. Security and destructive installer changes require extra caution.

## Becoming a maintainer

Consistent contributors may be invited to maintain an area after demonstrating sound review judgment, respectful collaboration, and sustained familiarity with that subsystem. Access should follow least privilege and can be revisited when someone becomes inactive.

## Project direction

The roadmap is public in [ROADMAP.md](ROADMAP.md). Roadmap items are goals, not promises or deadlines.

## Changes to governance

Governance changes should be proposed publicly and receive broader review than ordinary implementation changes.
